# Type-7 evidence decision

Status: unresolved; preserved and blocking for lossless certification.

The supplied compatibility manifest records eight `DO_TYPE=7` rows in the
observed SQLite source. The supplied XLSX export contains no corresponding
rows. That proves an export difference, not the meaning of the type: the
available evidence does not identify whether type 7 is a transfer, adjustment,
fee, settlement, or another product behavior.

Decision: keep type 7 outside the mapped economic model. Preserve each value
with source provenance, surface a registered unresolved-semantic reason, and
block any zero-loss or behavioral-parity certification until a synthetic oracle
and before/after behavior tests establish its semantics.

Evidence: `research/compatibility/supplied-backup-manifest.json`,
`research/compatibility/supplied-artifact-manifest-2026-08-10.json`, and
`research/compatibility/waves/wave-03/shard-xlsx-export.md` in the immutable

## Update 2026-11-01

Status: provisionally resolved as a balance decrease; still blocking until one test
backup confirms it.

New evidence: the owner reports that editing an account balance creates an entry in
the "Difference" category, shown as an expense when the balance goes down and as income
when it goes up. In the 2026-11-01 backup, every type-7 row uses the built-in category
`-4`, increases appear as `DO_TYPE=0` rows with `-4`, and no `DO_TYPE=1` row uses `-4`.
So type 7 is the decrease side of a balance edit, an outflow from `assetUid` by `ZMONEY`.

Next step: a backup taken after one known test decrease. If it adds exactly one type-7
row with that amount, map type 7 as an outflow and remove the block. Details in
