Why your real backup cannot load yet

  • Semantics are unproven, structure is not enough

    Your database identifies itself as schema v19 and the inspector can account every table and row. Identification is level L0. Before one row of your data commits, the importer must prove what each code means: which DO_TYPE value is a transfer, what the fee link points at, how PERIOD_TYPE slices months, and what transaction type 7 even is. Guessing wrong inverts balances silently, so the constitution forbids the guess.

    Tracks: #8 #9 #10 #11

  • The oracle problem

    Proof requires comparing Ledger Atlas output against the original app on the same synthetic data: balances, report totals, rounding, date boundaries. Those before-and-after captures do not exist yet. Research tickets 08 through 13 define exactly which proofs are missing.

    Tracks: #8 #9 #10 #11 #12 #13

  • Photos cannot survive the trip

    The PHOTO table holds 1,478 metadata rows. The image bytes live outside the database and none were supplied. An import today would lose every receipt, which breaks the lossless-or-loud rule, so the importer refuses instead of lying.

    Preservation tracks #12; byte export is a device action (#32).

  • Settings are opaque blobs

    The ZETC table stores app settings as integer datatype keys with encoded values, 34 of them. One decodes to a Korean locale marker. Without a mapping for those keys, migrated settings would be noise, so they stay out.

    Oracle-gated decode: human-supervised, see #32.

  • The real-backup write path is unfinished

    mmctl can classify, inspect, stage and reconcile supported synthetic data. It cannot yet populate a trusted canonical ledger from the supplied Android v19 evidence. The blocker is incomplete mapping and reconciliation, not commit permission.

    Tracks: #5 #13
